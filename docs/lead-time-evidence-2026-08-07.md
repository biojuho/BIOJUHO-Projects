# 리드타임 실증 (2026-08-07)

이 문서는 레이더가 **얼마나 일찍** 잡는지에 대한 첫 실측이다.  
관측 원본 `automation/getdaytrends/data/viral_lead_times.json`은 **읽기만** 했다.

재측정:

```bash
cd automation/getdaytrends
python scripts/report_lead_time_evidence.py data/viral_lead_times.json
```

---

## 1. 리드타임 정의

**리드타임(분) = `aggregator_first_seen_at` − `direct_first_seen_at`.**

- **양수:** 우리가 커뮤니티 **직접 목록**에서 글을 먼저 봤고, 그 뒤에 IssueLink(애그리게이터)에 같은 글이 나타났다. “일찍 잡았다.”
- **0:** 같은 수집 회차에서 양쪽을 동시에 처음 봤다(`same_poll`). 선행을 주장하지 않는다.
- **음수:** 애그리게이터가 먼저였고 우리는 나중에 직접 목록에서 봤다. “늦게 잡았다.”

측정 단위는 게시 시각 추정이 아니라 **이 수집기가 실제로 관측한 시각**이다.  
화면의 `measured_lead_count`는 위 정의 중 **양수(status=`measured`)만** 센다. 음수·동시·미쌍은 카운트에 안 들어간다.

---

## 2. 표본

| 항목 | 값 |
|------|-----|
| 원본 파일 | `data/viral_lead_times.json` (운영 경로, 2026-08-07 09:35 KST 전후 크기 ~975KB) |
| `updated_at` | 2026-08-07T00:35:08Z |
| 관측 구간(UTC) | 2026-08-05T22:54 → 2026-08-07T00:35 (**약 25.7시간**) |
| 저장 레코드 수 | **4,707** |
| 양쪽 시각이 있는 쌍(paired) | **29** (전체의 **0.6%**) |
| 증거 등급 | paired 29건 → **방향성~예비** (10 미만은 결론 금지, 50 미만은 예비) |

10건 미만 규칙은 통과했지만, **29건은 여전히 작다.** 아래 중앙값·비율은 예비 수치로 읽고, 며칠 더 쌓인 뒤 같은 스크립트로 재측정해야 한다.

## 3. 결과

### 3.1 측정 가능 여부 (왜 화면에서 12건 중 1건인가)

| 상태 | 건수 | 의미 |
|------|------|------|
| `awaiting_aggregator` | 4,069 | 직접 목록만 봄. IssueLink에 아직/끝내 안 뜸 |
| `aggregator_only` | 609 | 애그리게이터만 봄 (직접 수집 대상이 아니거나 직접에서 못 봄) |
| `measured` (양수 리드) | 26 | 직접이 먼저 |
| `same_poll` | 2 | 동시 첫 관측 |
| `aggregator_first` (음수) | 1 | 애그리게이터가 먼저 |

**핵심:** 레코드의 99% 이상은 리드타임을 **계산할 수 없다.**  
화면 `measured_lead_count`가 12건 중 1건인 것은 버그라기보다, (1) 표시 후보 대부분이 IssueLink와 쌍을 못 이루고 (2) 양수 리드만 세기 때문이다.

### 3.2 부호 있는 리드타임 (paired 29건만)

| 지표 | 값 |
|------|-----|
| 중앙값(전체 부호 포함) | **+80.0분** |
| 평균(참고, 이상치 큼) | +220.7분 |
| 양수(일찍) | 26건 (**89.7%**), 중앙값 +94.2분 |
| 음수(늦게) | **1건 (3.4%)**, −123.9분 |
| 0(동시) | 2건 (6.9%) |

분bucket:

| 구간 | 건수 |
|------|------|
| < −60분 (늦게) | 1 |
| 0 | 2 |
| 0–15분 | 1 |
| 15–60분 | 10 |
| 60–180분 | 7 |
| > 180분 | 8 |

양수 리드의 꼬리가 길다(최대 약 +16시간). 평균을 믿으면 안 되고 **중앙값**을 쓴다.

### 3.3 소스별 (paired만)

| 소스 | paired | 중앙값(분) | 양수% | 음수% |
|------|--------|------------|-------|-------|
| ruliweb | 21 | +44.0 | 90.5 | 0.0 |
| theqoo | 8 | +533.0 | 87.5 | 12.5 |

**보배·뽐뿌·개드립·오유 등 다른 직접 소스는 paired 0건.**  
직접 관측은 수백 건씩 쌓이지만 IssueLink와 `source:id` 키가 겹친 적이 없다.  
즉 현재 “얼마나 일찍” 숫자는 사실상 **루리웹·더쿠 두 채널의 예비 표본**이다.

## 4. 해석 (다음 개선 방향)

1. **조기 탐지 자체는, 쌍이 성립할 때, 대체로 먼저다.**  
   paired 29건 기준 음수 3.4%, 중앙값 +80분. 다만 표본이 작고 소스가 둘뿐이다.

2. **병목은 “리드가 짧다”가 아니라 “측정이 안 된다”.**  
   쌍 비율 0.6%. IssueLink에 안 오르는 글·키 불일치·직접 미수집 커뮤니티가 대부분을 삼킨다.  
   화면 선행 건수가 낮아 보이는 1차 이유는 여기다.

3. **개선 후보 (이 문서 범위 밖, 방향만):**  
   - 애그리게이터 슬러그와 직접 소스 키 정합(과거 `bobaedream`/`bobae` 류)을 전 소스에서 재점검  
   - IssueLink 외 교차 기준(조회 임계 돌파 시각 등) — 정의가 바뀌면 별도 지표로 분리  
   - 소스별 paired가 쌓일 때까지 중앙값을 “전체 레이더 성적”으로 승격하지 말 것

4. **자기기만 방지:** 양수 중앙값만 보여 주면 안 된다. 음수 비율(3.4%)과 미쌍 비율(99.4%)을 같이 본다.
